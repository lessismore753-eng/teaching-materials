AGENT 02 / EVALUATION / v0.3.2

Evaluation

讀取 Design Agent 做出的 Figma 設計稿，依照 JSON 規格逐項檢查元件、圓角、陰影、尺寸與間距是否正確，最後產出一份可直接交給 Fix Agent 使用的檢核報告。

01 · DESIGN02 · EVALUATION03 · FIX
Input · 輸入
Design Agent 產出的Figma 設計稿、要檢查的範圍，以及對應的JSON 規格
Output · 輸出
一份可設定檢查範圍的檢核報告，並整理成 Fix Agent 可以直接處理的問題清單
從 0 建立 Evaluation Agent

如果要從頭把 Evaluation Agent 建起來，建議固定用下面六個項目來寫。先把目標、輸入、檢核規則、輸出格式、驗收標準與禁止事項定清楚，再把內容整理成 Agent 指令。

步驟 1｜定義 Agent 的目標｜點擊圖片可放大

步驟 1｜定義 Agent 的目標

在實際開始前，先定義為什麼要有這個 Agent，以及它在整體流程中要解決什麼問題。可以先回答以下問題：

A. 為什麼需要建立這個 Agent？

B. 它在 Design、Evaluation、Fix 的流程中扮演什麼角色？

C. 完成工作後，應該為下一個階段帶來什麼結果？

把答案整理後，再寫成一段明確的目標，例如：

「你的工作是讀取 Design Agent 產出的設計稿，依照既有規格找出可確認的設計問題，並整理成一份可交給下一階段使用的檢核報告。」
步驟 2｜準備輸入資料｜共 2 張，可使用左右箭頭切換

步驟 2｜準備輸入資料

確定 Agent 的目標後，下一步是整理它執行檢核時需要讀取的資料，以及這些資料放在哪裡。可以先盤點現有資料與缺口：

A. 元件的 JSON 規格是否已經建立完成？

B. Figma Library 與 JSON 的位置是否已更新到 Main Guideline？

C. Design Agent 產出的設計稿要用什麼方式交給 Evaluation Agent？

D. 目前使用的 AI 工具是否已開啟 Figma、Notion 等 MCP 或必要的讀取權限？

E. 找不到設計稿、JSON 或元件庫時，Agent 應該停止、略過，還是請使用者補資料？

確認後，把開始檢核前的條件寫進 Agent 指令，例如：

「開始檢核前，先確認已取得目標 Figma 檔案、頁面、檢核範圍、對應的 JSON 規格，以及正式元件庫的讀取權限。預設只檢查使用者指定的畫面或元件。如果缺少必要資料，請停止該項檢核，列出缺少內容與無法執行的原因，不得自行補規格。」
步驟 3｜設定檢核規則｜共 3 張，可使用左右箭頭切換

步驟 3｜設定檢核規則

資料準備好之後，要決定 Agent 實際怎麼檢查。這一段只處理檢查範圍、檢查項目與執行順序，不處理報告格式或最終是否通過：

A. 每次要檢查哪一個頁面、畫面、區塊或元件？範圍多大？

B. 要固定檢查哪些面向，例如正式元件、元件狀態、樣式、圓角、陰影、尺寸與間距？

C. 數值要檢查到多細？是否允許誤差或例外？

D. 檢查順序是否要固定，避免 Agent 憑畫面感覺直接下結論？

確認後，把檢核面向與順序寫成固定流程：

①確認檢查範圍 → ②找到對應 JSON → ③讀取實際 Figma 資料 → ④逐項比對規格 → ⑤合併相同原因的問題 → ⑥整理檢核結果
「只檢查使用者指定的範圍。依序確認正式元件、元件狀態、顏色與文字樣式、圓角與陰影、尺寸與間距，以及裁切、重疊或超出範圍等問題。JSON 未定義的項目不得自行判定。」
步驟 4｜設定輸出格式｜共 2 張，可使用左右箭頭切換

步驟 4｜設定輸出格式

檢查方式確定後，再從下一階段的使用需求反推報告要怎麼呈現。這一段只定義報告的使用者、欄位、格式與放置位置：

A. 報告要提供給 Fix Agent、設計師，還是兩者都要看？

B. 報告要使用表格、文字框，還是其他固定格式？

C. 每一筆問題需要包含哪些欄位？

D. 最終報告要放在哪個檔案與位置？

確認後，把輸出格式固定下來，例如：

「每個問題至少要包含問題編號、問題位置與 Node ID、目前值、預期值、規格來源、建議修法與驗收方式。報告要讓 Fix Agent 與設計師都能閱讀，並放在主要設計畫面右側的獨立報告框。」
步驟 5｜設定驗收標準｜共 2 張，可使用左右箭頭切換

步驟 5｜設定驗收標準

最後要定義什麼情況才算檢核完成，以及整體結果要如何判定，避免 Agent 只跑完流程就自行宣告通過：

A. 指定的檢查範圍要完成到什麼程度，才算本次檢核結束？

B. 什麼條件可以判定通過？什麼條件必須判定有問題？

C. 規格未定義、資料讀不到或來源互相衝突時，要如何標示？

D. 什麼情況下不得判定通過，而必須交由人工確認？

確認後，把完成與判定條件寫清楚，例如：

「只有在指定範圍已檢查完成、所有已定義規格都有結果，而且每個問題都有明確證據時，才算完成。規格未定義、資料無法讀取或來源衝突時，必須另外標示為待確認，不得直接判定通過。」
步驟 6｜設定禁止事項｜點擊圖片可放大

步驟 6｜設定禁止事項

最後列出 Agent 絕對不能做的事，避免它在資料不足時越權修改、猜測規格或捏造證據：

A. 哪些產品畫面、正式元件、樣式或規格來源不能被修改？

B. 哪些情況不能用個人經驗或其他文件補上 JSON 沒寫的規則？

C. 哪些 Node ID、數值、樣式套用狀況或規格來源不得自行推測？

D. Fix Agent 修正後，應由誰重新檢查並決定是否完成？

確認後，把禁區直接寫進 Agent 指令，例如：

「禁止修改產品畫面、正式元件庫與規格來源；禁止用個人經驗補上 JSON 未定義的規則；禁止把仿製或拆開的元件視為正式元件；禁止捏造 Node ID、數值或規格來源。Fix Agent 修正後，必須交回 Evaluation Agent 重新檢核，不能自行宣布完成。」
關鍵重點
重點 01

先把六個項目定義清楚

目標、輸入、檢核規則、輸出格式、驗收標準與禁止事項，這六個項目如果寫得夠清楚，Agent 的執行結果通常會更穩定。

重點 02

檢查起點要小，不要一開始掃全檔

先從指定畫面或指定元件開始，才容易建立穩定流程，也比較方便和 Fix Agent 做來回修正。

重點 03

報告要能直接交接

真正有價值的輸出不是抓到錯，而是讓 Fix Agent 看完就能動手修，不需要再回頭追資料。

重點 04

規則與報告要分開設定

檢核規則負責定義怎麼檢查；輸出格式負責定義結果怎麼呈現。兩者分開，後續調整規則時才不會連帶破壞報告結構。

AGENT 03 / FIX / v0.2.1

Fix

讀取檢核 Agent 已確認的問題與 JSON 預期值，針對指定的 Figma 節點做最小幅度、可追蹤的局部修正。每次修改後都要重新讀取節點，確認修正是否真的寫入，最後交回檢核 Agent 重新檢查。

01 · 設計02 · 檢核03 · 修正
輸入資料
檢核 Agent 提供的已確認問題、對應 JSON 規格，以及目標 Figma 節點的讀寫權限
輸出結果
修正後的 Figma 節點、一份修正紀錄表，以及交回檢核 Agent 的重新檢查清單
從 0 建立修正 Agent

修正 Agent 具備直接改動設計稿的能力，因此重點不是「修得越多越好」，而是把可修範圍、停止條件、驗證方法與交接方式寫清楚。建議固定使用下面六個步驟。

步驟 1｜定義修正目標｜圖片預留區，可自行替換

步驟 1｜定義修正目標

檢核 Agent 已經找出問題，但「知道哪裡錯」不代表可以直接全面重做。第一步要先說清楚修正 Agent 在流程中的角色：

A. 修正 Agent 只處理哪些已確認的問題？

B. 允許修改哪些節點與屬性？修正範圍要多小？

C. 修正完成後，由誰重新檢查並判定是否通過？

把答案整理後，再寫成明確的目標，例如：

「你的工作是讀取檢核 Agent 已確認的問題，依照 JSON 規格，針對指定的 Figma 節點做最小幅度的局部修正。每次修改後都要重新讀取實際節點，確認修正是否真的寫入，並把修正紀錄交回檢核 Agent 重新檢查；你不能自行宣告問題已正式通過。」
步驟 2｜準備輸入資料｜圖片預留區，可自行替換

步驟 2｜準備輸入資料

修正 Agent 不能只收到一句「這裡有問題」就開始修改。開始前，要先確認每一筆問題是否具備足夠資訊：

A. 是否包含問題編號與目標節點 ID？

B. 是否寫清楚目前值、JSON 預期值與規格來源？

C. 是否提供修正方式、驗收條件，以及可修改與不可修改的範圍？

D. Agent 是否具備目標 Figma 節點的讀取與寫入權限？

E. 沒有可處理的問題，或資料不完整時，應該怎麼回報？

確認後，把開始條件寫進 Agent 指令，例如：

「開始修正前，先確認每個問題都包含問題編號、目標節點 ID、目前值、JSON 預期值與來源、修正方式、驗收條件，以及可修改與不可修改的範圍。資料不完整時標示 needs-review（需人工確認）；無法讀寫目標節點時停止執行；沒有可處理的問題時回報 no-action（無需處理）。」
步驟 3｜設定修正規則｜圖片預留區，可自行替換

步驟 3｜設定修正規則

資料完整後，接著要限制 Agent 可以怎麼修。修正 Agent 的價值不是「改得多」，而是「只改必要的地方，而且能證明真的修改成功」：

A. 哪些類型的問題可以由修正 Agent 處理？

B. 修改範圍是否只限於達成驗收條件所需的節點與屬性？

C. 正式元件、顏色、文字與圖示，是否必須使用正式元件實例或樣式綁定？

D. 檢核報告、JSON 與實際 Figma 資料互相衝突時，是否要停止修改？

E. 修改後是否要檢查上層、同層節點，以及裁切、重疊、溢位等連帶影響？

建議把修正流程固定為：

①讀取可處理的問題 → ②讀取對應 JSON → ③重新讀取目標節點 → ④執行最小修正 → ⑤重新讀取修正後節點 → ⑥檢查連帶影響
「只處理已確認且資料完整的問題。正式元件必須使用正式元件實例；顏色、文字、圖示、框線與陰影必須使用正式樣式綁定，不得只填入相同數值。只修改達成驗收條件所需的最小範圍；如需跨區域修改，或檢核報告、JSON 與 Figma 互相衝突，立即停止並標示 needs-review（需人工確認）。」
步驟 4｜設定輸出格式｜圖片預留區，可自行替換

步驟 4｜設定輸出格式

修正完成後，不能只留下「已完成」三個字。輸出內容必須讓設計師與檢核 Agent 看得懂修改內容，也能直接重新驗收：

A. 每個問題要記錄哪些修改前後資訊？

B. 未修正的問題與原因是否也要保留？

C. 修正結果要放在 Figma 的哪個位置？

D. 交回檢核 Agent 時，要提供哪些重新檢查的資料？

確認後，把輸出格式固定下來，例如：

「在檢核報告右側建立『修正 Agent｜修正結果｜<主要畫面名稱>』報告框，不得覆蓋原報告或移動產品畫面。輸出內容需包含執行狀態、修正摘要，以及每個問題的目標節點 ID、修正項目、修改前、修改後、結果與待確認事項；最後列出要交回檢核 Agent 重新檢查的問題、節點與 JSON 規格。」
步驟 5｜設定驗收標準｜圖片預留區，可自行替換

步驟 5｜設定驗收標準

最後要定義「修改完成」與「正式通過」的差別。這是修正 Agent 最容易越權的地方：

A. 什麼情況可以標示「修正已套用」？

B. 修改失敗或修改後仍不符合規格時，要使用什麼狀態？

C. 規格衝突、節點已變更，或無法安全地局部修正時，要如何處理？

D. 整次修正要在什麼情況下標示已完成、執行失敗、需人工確認或無需處理？

E. 誰有權判定問題已正式通過？

確認後，把驗收標準寫清楚，例如：

「只有在修正已成功寫入，而且重新讀取的節點符合 JSON 預期值時，才能標示 fix-applied（修正已套用）。未成功或修改後仍不符合時標示 not-applied（未成功套用）；規格衝突、節點已變更或無法安全局部修正時，標示 needs-review（需人工確認）。修正已套用只代表修改完成，最終是否通過，必須由檢核 Agent 重新檢查後判定。」
步驟 6｜設定禁止事項｜圖片預留區，可自行替換

步驟 6｜設定禁止事項

修正 Agent 具備直接修改設計稿的能力，因此禁止事項必須比一般 Agent 更明確。可以先確認：

A. 是否禁止修正檢核報告沒有列出的問題？

B. 是否禁止用其他文件、個人經驗或偏好，補上 JSON 沒寫的規格？

C. 是否禁止修改主元件、變數、文字樣式、正式元件庫或範圍外的節點？

D. 是否禁止用一般畫框、手動填入的數值或相同數值，冒充正式元件或樣式綁定？

E. 是否禁止在未實際寫入，或未經檢核 Agent 重新檢查前宣告完成？

確認後，把禁區直接寫進 Agent 指令：

「不得修正檢核報告未列出的問題；不得用 Markdown、GitHub、一般介面設計經驗或個人偏好補上 JSON 沒寫的規格；不得修改主元件、變數、文字樣式、正式元件庫或範圍外節點；不得用一般畫框、手動數值或相同數值冒充正式資產與樣式綁定；未實際寫入不得宣稱修正完成，也不得把 fix-applied 說成正式通過。」
關鍵重點
重點 01

只修已確認、可處理的問題

問題資料不完整、規格衝突，或無法安全地局部修正時，修正 Agent 的正確做法是停止，不是猜測。

重點 02

最小修正比全面整理更重要

只修改達成驗收條件所需的節點與屬性，不順便整理畫面，也不擴大影響範圍。

重點 03

每次修改後都要重新讀取

Agent 不能只根據執行指令就認定修改成功，必須重新讀取實際 Figma 節點，並檢查是否造成其他問題。

重點 04

修正 Agent 不負責正式判定通過

fix-applied 只代表修正已成功套用；問題是否正式關閉，仍由檢核 Agent 重新檢查後決定。
