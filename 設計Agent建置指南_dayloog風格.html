為什麼要做這件事

AI 時代下的設計變革

去年我們做了許多 AI 嘗試，打下了底子。今年，整個組織都在盤點如何把 AI 真正融入設計流程——而我們要交出的，不只是零星的嘗試，而是一套自己實際跑得動的 Design Workflow。

這套 workflow 的架構，是產險驗證過、方向可行的流程，也會是 UED 未來共用的工作方式。但它要靠你們親手建起來——因為你們是最清楚 AI Agent 建置細節的人，一個環節能不能成立、怎麼串才順，只有實際做的人最有體會。

我們已經把每一步的做法、可能踩到的坑整理在這個網站上。過程中有任何問題，隨時來找我們。

// PRINCIPLES

建置原理

在動手做任何一個 Agent 之前，先理解這幾個原理 —— 它們會決定三個 Agent 串起來會順跑、還是會互相打架。

Tool-agnostic

先講一件重要的事：這套架構跟你用哪個工具無關。以 Claude Code、Figma Agent、Codex 這三個為主，都能實作出下面這組 agent —— 差別只在介面與串接方式，不在能不能做。

01

檢查者，要跟生成者隔離

Evaluation Agent 絕對不能看到 Design Agent 是「怎麼想的」。如果它讀得到生成時的推理過程，它會順著那套邏輯點頭 —— 生成者說「這裡留白是刻意的」，檢查者就會同意，於是審查失去意義。

把兩個 Agent 拆成獨立的 Skill / 對話，別讓它們共用同一段上下文。檢查者的輸入只餵兩樣：Design 的產出結果與 Notion 上的規範 —— 生成時的推理過程一律不傳進去。
02

迴圈要有上限，跑不過就轉人工

Evaluation → Fix → 再 Evaluation 是一個迴圈。沒有上限，它可能無限地修下去。重試上限的意義不是「湊到幾輪」，而是「什麼時候該讓人接手」。

怎麼做在迴圈裡設一個計數上限（預設 3 輪）當停損。另外加一條收斂判斷：連續兩輪問題數沒下降就提前停。任一條件觸發，就把最後一份問題報告交給設計師人工處理。

上限管的是交棒時機，不是完美程度。跑滿還沒過，就把最後一份問題報告交給設計師，而不是讓 Agent 繼續繞。
03

哪些要跟 UED 一致，哪些可以自己決定

三個 Agent 大部分的實作細節都可以彈性 —— 用哪個工具、prompt 怎麼寫、複雜頁面跑幾輪，都由你自己決定。但有一件事必須全隊統一。

一致的地方：規範一律放在 Notion，而且 Notion 上資料的擺放方式（資料庫結構、欄位、命名）要跟團隊一致 —— 因為三個 Agent 都讀同一份，擺法不一致，agent 就抓不到。其餘（工具、prompt、輪數）都可彈性。
承上 · 重試要跑幾輪

預設 3 輪，
由設計師依複雜度自訂

沒有一個放諸四海皆準的輪數。簡單的頁面可能 1–2 輪就收斂，複雜的頁面可以往上調到 5 輪。所以把上限設計成可調的 —— 預設 3 輪當起點，設計師依頁面自己決定要不要加。但「可調」不等於「無限往上加」。調整的依據是收斂，不是完美。

停損邏輯 A · 收斂判斷

連續兩輪抓到的問題數沒有下降（甚至變多），那不是輪數不夠，是 Fix 或規格本身有問題。這時該停，加再多輪也沒用。

停損邏輯 B · 上限即轉人工

跑滿設定輪數還沒過，就把 Evaluation 最後一份報告交給人工處理，而不是取消上限讓 Agent 自己硬幹。

三個 Agent 共通的一件事

三份報告的欄位規格要能對接 —— 至少 component ID、rule ID、狀態要一致。Design 輸出「用了哪些元件」、Evaluation 輸出「逐條 pass/fail」、Fix 輸出「改了什麼」。用同一套 ID 系統，orchestration 才串得起來。這件事在每個 Agent 的「設定報告輸出方式」那一步都要遵守。

AGENT 01 / GENERATION

Design

產線的起點。依照元件規範產出設計稿，並回報它用了哪些元件、套了哪些規則 —— 這份回報，就是後面兩個 Agent 的檢查對象。

01 · DESIGN02 · EVALUATION03 · FIX
Input · 輸入
設計需求 ＋ Notion 上的元件規範（色票 / size token / 禁用規則 / 決策邏輯）
Output · 輸出
Figma 設計稿 ＋ 一份使用清單：用了哪些 component ID、套了哪些 rule ID
建置步驟

這個 Agent 的前幾步，同時也在建立後面兩個 Agent 共用的資料層（規範來源與 Notion 資料庫）。先把地基打好，再實作 Skill。

01

用 Figma Skill 建立 Component 規格

透過 Figma MCP，把元件的規格抽出來 —— 每個 component 的色票、尺寸、間距、狀態。這是整條產線的「事實基準」。

Figma MCP · component spec
02

用 Skill 產出 Component 的 MD 檔案

把規格轉成 MD。MD 負責人看得懂的語意與 edge case —— 為什麼這樣設計、什麼情況例外，這些是 JSON 表達不了的脈絡。

MD · 語意與 rationale
03

人工審查 MD 檔案是否正確

Agent 抽出來的規格不一定對。這一步由設計師親自核對，確認 MD 忠實反映真正的規範，才放行。這是唯一必須有人的環節。

Human review
04

設定報告輸出方式

定義 Design Agent 產出設計後，要附上什麼格式的「使用清單」。至少包含 component ID 與 rule ID —— 這是交給 Evaluation 的接口。

handoff · 共用 ID 規格
05

建立 Notion 資料庫

把規範放進 Notion，當作三個 Agent 共同讀取的儲存與協作層。Notion 對非技術設計師友善，也避開 GitHub 的公司審核門檻。三個 Agent 讀同一份，事實基準才一致。

Notion MCP · 共用資料層
06

建立 Skill 並實作

把上面這套流程寫成一個 Skill：讀 Notion 規範 → 產出設計 → 附上使用清單。實測產出是否穩定、清單格式是否正確。

Skill · 實作
交接提醒

Design Agent 的產物不只是「一張設計稿」。真正重要的是那份使用清單 —— 它是 Evaluation Agent 唯一能拿到的、關於「這張稿子聲稱自己做了什麼」的資訊。清單寫得含糊，後面就無從查起。

AGENT 02 / EVALUATION

Evaluation

產線的把關者。它不管設計「好不好看」，只管「有沒有違反規範」。逐條比對，產出一份可勾選的 pass / fail 清單 —— 這份清單，就是 Fix Agent 的工作單。

01 · DESIGN02 · EVALUATION03 · FIX
Input · 輸入
Design 的使用清單 ＋ Notion 上的規範（同一份，不另抽）
Output · 輸出
一份逐條問題報告：每條 rule 標記 pass / fail，fail 附上違反了什麼
關鍵原則

Evaluation Agent 只能拿到「產出結果」與「規範」兩樣東西 —— 絕不給它看 Design Agent 的推理過程，否則會被帶著走。它的任務是對抗式找碴，不是打分數：不要它給設計稿打 85 分（稽核時沒人知道那 15 分扣在哪），而是逐條列出「違反了哪條 rule ID、在哪個 component」。判準也不能是「整體感覺不夠精緻」，必須是可逐項勾選的規則清單（就是下面那份 JSON 判準）。

建置步驟
01

用 Figma Skill 建立 Component 規格

取得要檢查的規格基準。注意：如果 Design Agent 已經抽過同一批 component，這裡讀 Notion 上那份就好，不要重抽。兩邊的事實基準必須是同一份，否則檢查會失準。

讀取 · 不重抽
02

用 Skill 建立 JSON 檔案

這一步不只是「產一個 JSON」，而是把審查標準結構化成 JSON：hex、size token、禁用規則，一條一條列成可以逐項核對的清單。這份 JSON 就是檢查者的判準。

JSON · 可勾選判準
03

設定報告輸出方式

定義問題報告的格式：每一條 rule ID 對應一個狀態（pass / fail），fail 要註明對象 component ID 與違反內容。這份報告是 Fix Agent 的直接輸入，欄位要對得上。

report · Fix 的工作單
04

建立 Skill 並實作

把流程寫成 Skill：讀使用清單 ＋ 讀 JSON 判準 → 逐條比對 → 輸出問題報告。實測它能不能穩定抓出真正的違規，而不是含糊帶過。

Skill · 實作
判準清單長什麼樣（示意）

JSON 判準攤開來，大概就是這樣一份可以逐格打勾的東西。每一條都明確、可核對、有 ID：

Eval report · sample
R-COLOR-01主色 hex 是否等於 token 定義值
R-SIZE-04間距是否使用 size token，未寫死數值
R-BAN-02是否踩到禁用規則（如禁用的圓角 / 陰影）
R-COMP-07是否使用了規範外的自製元件

AGENT 03 / FIX

Fix

產線的收尾者。它不重新設計，只針對 Evaluation 報告裡的每一條 fail，依規則修正。修完交還 Evaluation 再檢查 —— 這個迴圈由它管理，包括什麼時候該停。

01 · DESIGN02 · EVALUATION03 · FIX
Input · 輸入
Evaluation 的問題報告 —— 這是 Fix 的工作來源，沒有它 Fix 不知道要修什麼
Output · 輸出
修正後的設計 ＋ 一份變更報告：改了哪些 component、對應哪些 rule ID
先接對輸入

Fix Agent 最容易被漏掉的一件事：它的輸入是 Evaluation 的問題報告。設定修復規則之前，要先確定它吃的是那份逐條報告，規則是「針對報告裡的每一條 fail，該怎麼修」。沒接上這條線，會做出一個不知道要修什麼的 Fix Agent。

建置步驟
01

設定修復規則

定義「看到某一類 fail，該怎麼修」。以 rule ID 為單位：R-COLOR-01 fail → 換回 token 定義的 hex。同時在這裡寫入重試上限（預設 3 輪）與收斂停損：連續兩輪問題數沒下降就停、跑滿還沒過就轉人工。

rules · 含重試上限與收斂
02

設定報告輸出方式

定義變更報告格式：改了哪些 component ID、對應處理了哪些 rule ID、還有哪些沒能修好。欄位要能跟 Evaluation 對接，這樣下一輪檢查才知道要重驗哪幾條。

report · 回傳給 Evaluation
03

建立 Skill 並實作

把流程寫成 Skill：讀問題報告 → 逐條套修復規則 → 產出變更報告 → 交還 Evaluation。實測整個迴圈跑得動、會在該停的時候停、跑滿會轉人工。
