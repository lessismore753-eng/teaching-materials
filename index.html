AI 時代下的設計變革

當整個組織都在盤點如何把 AI 融入工作流程——我們更要有自己的 UED Workflow。

本教材中 workflow 的架構，是AI小組驗證過、方向可行的流程，也會是 UED 未來共用的工作方式。但它要靠你們親手建起來——因為你們是最清楚 AI Agent 建置細節的人，一個環節能不能成立、怎麼串才順，只有實際做的人最有體會。

我們已經把每一步的做法、可能踩到的坑整理在這個網站上。過程中有任何問題，隨時來找我們。

// PRINCIPLES

建置原理

在動手做任何一個 Agent 之前，先理解這幾個原理 —— 它們會決定3個 Agent 串起來會順跑、還是會互相打架。

Tool-agnostic

工具以 Claude Code、Figma Agent、Codex 這3個為主，差別只在介面與串接方式。

01

檢查者，要跟生成者隔離

Evaluation Agent 建議不讓他看到 Design Agent 的生成脈絡，如果它讀得到生成時的推理過程，它會順著那套邏輯點頭。例如生成者說「這裡留白是刻意的」，檢查者就會同意，於是審查失去意義。

把2個 Agent 拆成獨立的 Skill / 對話，別讓它們共用同一段上下文。檢查者的輸入只餵 Design 的產出結果與 Notion 上的規範就好。
02

迴圈要有上限，跑不過就轉人工

Evaluation → Fix → 再 Evaluation 是一個迴圈。沒有上限，它可能無限地修下去。重試上限的意義不是「湊到幾輪」，而是「什麼時候該讓人接手」。

可以在迴圈裡設一個計數上限（例如 5-10 輪），另外加一條收斂判斷如：連續2輪問題數沒下降就提前停。若已經確定 Loop 已經抵達極限，就把最後一份問題報告交給設計師人工處理，而不是讓 Agent 繼續空轉。
03

哪些要跟 UED 一致，哪些可以自己決定

3個 Agent 大部分的實作細節都可以彈性設置，例如用哪個工具、prompt 怎麼寫、Design System 內容、複雜頁面跑幾輪，你都可以自己決定。但規範必須放在 Notion 。

Notion 上資料的擺放方式建議跟團隊一致，這樣未來技術更新的時候，workflow 的整合會更順暢。
04

3個 Agent 共通的一件事

3個 Agent 都需要遵循相同的 Notion 資料庫、資料格式和輸出規範，以確保資訊能夠順利傳遞和整合。

Component 文件檢查表
#項目必要性說明
1ID 與定位必要唯一 ID、名稱、它是什麼（按鈕／輸入框／卡片）。ID 是 3 個 agent 交接報告時互相對得上的錨點，不能省。
2視覺規格必要色票（用 token 名稱、非裸 hex）、尺寸、間距、圓角、字級字重、border、shadow —— 每項給明確數值或 token。
3狀態視情況default / hover / focus / active / disabled / error 各狀態的視覺差異。只要元件會互動就必填。
4變體 Variants視情況有哪些尺寸／樣式變體、各自改動哪些規格、哪些能組合哪些互斥。有變體才需要。
5禁用規則必要明確寫「不可以怎樣」：不可改的顏色、不可自製的變體、禁止的組合。對應 Evaluation 的 R-BAN-xx 判準。
6使用時機與決策邏輯建議什麼情況用這個、什麼情況用別的、跟相似元件怎麼區分。這是生成 agent「選對元件」的依據。
7Edge case 與例外建議文字過長怎麼顯示、無內容時要不要顯示 Component、超級有錢人的極端金額尺寸、有什麼無障礙要求（對比度、focus ring、aria）等等
03

利用 Skill 產出產品元件的 MD 及 JSON 檔案

套用以下文件建立 Skill，並建立產品元件的 MD 及 Json 檔案。接著把 Figma Agent 產出的元件文件交給轉檔 Skill，同時產出 2 種格式：

  • MD：提供設計師與 Design Agent 閱讀，說明元件用途、使用時機與限制。
  • JSON：提供 Evaluation 與 Fix Agent 讀取，保存 Variant、Property、Binding、尺寸與間距等可程式檢查的資料。
  • 檔名與 Component ID 必須一致，避免 Agent 找到錯誤版本。

# Tab-Stroke 使用規範

## 元件目的

`Tab-Stroke` 用於以底線（stroke）標示目前選中的分頁或導航項目。

來源顯示 `Tab-Stroke` 支援 Desktop 與 Mobile 兩種裝置尺寸，並可呈現 Icon＋文字、純文字、純 Icon 三種顯示模式。

## 適用情境

- 網站頂部主要導航。
- Desktop 上以 Icon＋文字模式協助使用者辨識功能區域。
- Mobile 上以純 Icon 模式節省螢幕空間。
- Mobile 上作為底部導航或功能分頁。
- Mobile 上以純文字模式呈現功能分頁。

## 元件選擇方式

```text
Desktop 尺寸
→ Tab-Stroke/Desktop

Mobile 尺寸
→ Tab-Stroke/Mobile

需要同時顯示圖示與文字
→ Show icon = true；Show Text = true

只顯示文字
→ Show icon = false；Show Text = true

只顯示圖示
→ Show icon = true；Show Text = false
```

## 元件特有的使用與禁止規則

### 使用規則

- `Tab-Stroke` 由原子元件 `Tab-Stroke/Desktop` 與 `Tab-Stroke/Mobile` 組成。
- 使用底線（stroke）標示選中狀態。
- `Tab-Stroke` 之間的間距可彈性設定。
- 顯示模式透過 `Show icon` 與 `Show Text` 布林屬性控制。
- Icon＋文字模式用於完整展示。
- 純文字模式需隱藏 Icon。
- 純 Icon 模式需隱藏文字。
- Desktop 網站主導航可使用 Icon＋文字模式。
- Mobile 可使用純 Icon 模式節省螢幕空間。

### 禁止規則

- 不得將示意文案視為 Tab 名稱規格，例如「住宅火災保險」、「汽車保險」、「旅行平安險」、「基本資料」、「進階設定」、「通知偏好」。
- 不得自行新增 Figma 未定義的顯示模式。
- 不得自行推測 `Show icon` 與 `Show Text` 以外的 Variant Property。
- 不得自行推測固定間距、尺寸、padding、gap、stroke 寬度或色彩 Token。
- 不得將 Desktop 與 Mobile 原子元件互換使用。

## 衝突與尚未定義事項

### 衝突

- undefined

### 尚未定義

- `componentId` 未在此 Figma node 可見內容中定義。
- `Tab-Stroke` 的正式分類未在此 Figma node 可見內容中定義。
- 選中狀態以外的狀態集合未定義。
- `Show icon` 與 `Show Text` 的正式 Figma Property 型別除布林敘述外未提供機器值。
- Icon 的正式資產名稱、替換規則與可用清單未定義。
- Text label 的字級、字重、行高與 Text Style 未定義。
- Stroke 的色彩、寬度、位置與 Token 未定義。
- Desktop 與 Mobile 的完整尺寸、padding、gap、min width、max width 未定義。
- 多個 Tab 之間「間距可彈性設定」的可用範圍未定義。
- 鍵盤操作、Focus、ARIA 與讀屏名稱未定義於此元件 node。
- 純 Icon 模式是否必須提供 tooltip 或可見輔助文字未定義於此元件 node。

04

人工檢查 MD／JSON 是否正確

AI 抽出的規格一定有一些小錯誤。由熟悉元件的設計師逐項核對 Figma Library、MD 與 JSON，確認名稱、狀態、數值、樣式綁定與禁用規則一致。

  • 缺少的規格標示可進行表示，例如 undefined，千萬別讓 Agent 自行猜測答案。
  • MD 與 JSON 內容矛盾時先修正文件，再進入下一步。
  • 確認 Agent 能依 Component ID 找到同一個元件。
05

把內容放上 Notion

將完成並通過人工檢查的內容放進組別的 AI Skills 文件庫，讓 Agent 可以從固定位置找到最新版本。

  • 檢查每個頁面的名稱、狀態、用途說明與版本是否正確。
  • 確認 Main Guideline 中的連結可以導向實際文件。
實作 / HANDS-ON

跑一次完整流程

建置完成後，可嘗試用一個需求，跑完 Design、Evaluation、Fix 與重新檢核這個流程。利用這段實作找出流程、文件與權限哪裡還不完整。

Input · 輸入
一個範圍明確的真實需求、指定的 Figma 位置，以及已完成的 Notion 規範與 3 個 Agent
Output · 輸出
一輪完整的 Agent 執行紀錄、設計／檢核／修正報告，以及需要回頭調整的待辦清單
實作步驟

第一次實作不要選太大的頁面。先確認整條線接得起來，再逐步增加頁面、狀態與元件數量。

01

選一個適合測試的真實需求

選擇範圍小、目的明確，而且主要使用正式元件的需求。建議不要選跨多頁、業務規則複雜或資料尚未確認的任務。

  • 建議先從單一頁面或單一流程開始。
  • 資料可以使用明確標示的測試內容。
  • 先以 Desktop 或團隊主要裝置版本驗證。
02

執行 Design Agent

負責依設計目的、目標裝置與需求建立畫面，並留下可供後續檢查的設計結果。

01Notion Link

貼上 Design Agent 連結

將 Design Agent 的 Notion 連結貼到 AI 對話框，讓 AI 讀取 Agent 的職責、執行流程與輸出格式。

Prompt 範例：https://app.notion.com/p/AI-Skills-e66396cc28ac40168318b07d995cf95b?source=copy_link
02Design Prompt

輸入完整的設計需求

Prompt 至少要包含設計目的、目標裝置與設計需求；有指定 Figma 位置時，也要一併提供。

Prompt 範例：幫我設計一個電腦版火災保險網頁，包含多個方案比較。
03Task Scope

提供任務邊界

在執行前提供任務、成功條件、Figma File、Page、目標位置、裝置、必要狀態，以及可修改與不可修改範圍。

Prompt 範例：「請在指定 Figma Page 的空白區域建立畫面。只使用 Notion 文件庫中的規範與正式 Library，不要移動或修改既有畫面；完成後輸出執行表格。」
03

執行 Evaluation Agent

負責依文件庫規範檢查 Design Agent 的產出，指出不合規的位置、檢查依據與待確認事項。

01New Context

開啟另一個 AI 軟體或對話框

使用另一個獨立的 AI 軟體或全新對話框，避免 Evaluation Agent 讀到 Design Agent 的生成脈絡。

02Notion Link

貼上Evaluation Agent 連結

將 Evaluation Agent 的 Notion 連結貼到新的 AI 對話框，檢查設計稿。

03Run Check

輸入檢查 Prompt

將 Evaluation Agent 的 Notion 連結貼到新的 AI 對話框，檢查設計稿。

Prompt 範例：執行檢查。
04

執行 Fix Agent

負責依已確認的 Evaluation 結果修改指定問題，不重新設計未被點名的區域。

01Review Issues

確認要交給 Fix 的內容

閱讀 Evaluation Agent 的輸出，確認問題與建議是否合理，並決定要讓 Fix Agent 執行的項目。

02Notion Link

貼上 Fix Agent 連結

將 Fix Agent 的 Notion 連結貼到 AI 對話框，並輸入修改需求。

03Run Fix

輸入修改 Prompt

將 Fix Agent 的 Notion 連結貼到 AI 對話框，並輸入修改需求。

Prompt 範例：執行修改。
05

重新檢核並確認結果

修改完成後，交回同一個 Evaluation Agent，依原本的 JSON 與驗收條件重新檢查。

  • 確認已修正的問題是否通過。
  • 確認修改沒有造成新的裁切、重疊或其他問題。
  • 仍無法通過的問題可通過修改 Agent、MD 檔案或直接轉人工處理。
06

整理卡點，回頭修正基礎資料

實作中遇到的問題，可以通過修正 MD/Json 檔案來解決。先判斷卡點來自那個流程，再修正對應來源：

卡點優先修正位置
找不到規範或元件Main Guideline、Notion 資料位置、文件命名
數值無法檢查Component JSON 的欄位與完整度
Agent 修改範圍過大Agent 職責、禁止事項、可修改範圍
報告無法交接3 個 Agent 的輸出欄位與 ID 系統
